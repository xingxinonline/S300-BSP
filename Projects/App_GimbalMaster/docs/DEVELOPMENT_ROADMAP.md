# App_GimbalMaster Development Roadmap

本文档把当前已落地的主板初始能力，整理成后续可执行的阶段路线。目标是先把单线程主循环骨架做稳，再决定是否需要 RTOS 化。

## 1. 当前基线

截至当前版本，主板 App 已具备以下初始能力：

1. 主板通过 I2C 协调子板启动，顺序为 `REQUEST_MASTER_MM_ENABLE -> PREPARE_VIDEO -> START_DSP`。
2. 子板进入 `RUNNING` 后，主板再启动本板 KWS 控制面与数据面。
3. 主板可持续轮询子板 `RESULT` 寄存器，并在本地显示链路上叠框。
4. 主板本地 KWS 能稳定运行，心跳与控制协议链路已打通。
5. 主板与子板模型路径和版本信息已进入构建期管理。

这意味着当前系统已经不是“Demo 拼接”，而是具备了一个清晰的正式 App 骨架。

## 2. RTOS 判断

当前阶段不建议立刻引入 RTOS，理由如下：

1. 主链路已经可运行，单线程主循环更利于继续定位协议、外设、模型和时序问题。
2. 现有工作负载仍然能被 `main.c` 中的 cooperative loop 清晰调度。
3. 现在引入 RTOS，复杂度会先上升，但不会直接带来功能收益。

建议保持“先做稳，再并发化”的策略。只有在后续多周期任务、阻塞点和实时性冲突明显增加时，再考虑 RTOS 化。

## 2.1 模块集成准入原则

后续所有模块在并入主板 App 之前，至少要先满足一个前置条件：

1. 仓库内已经有一个相应的、可独立构建并已实际跑通的 Demo。

这样做的目的不是增加流程，而是降低集成期的不确定性。主板正式 App 只负责系统集成，不应该同时承担“新模块首次 bring-up”和“多模块协同联调”两类风险。

建议把模块并入 App 前的准入门槛固定为：

1. 有独立 Demo 或最小验证工程。
2. Demo 已完成至少一次板上跑通验证。
3. Demo 的输入、输出、时序和资源占用边界是清楚的。
4. Demo 已知限制已经记录，不把未确认行为直接带入主板 App。

## 2.2 建议的集成顺序约束

按照这个原则，后续模块应采用“Demo 先行，再入 App”的顺序：

1. 先做模块级 Demo。
2. 再做接口抽象和日志口径整理。
3. 最后并入主板 App 主循环或动作层。

对于当前规划中的模块，建议这样执行：

1. 云台控制：先有舵机控制 Demo 或最小闭环 Demo，再并入 App。
2. IMU：先有姿态输出或防抖 Demo，再并入 App。
3. BLE HID：先有拍照/录像控制 Demo，再并入 App。
4. UWB：先有串口解析和目标角度输出 Demo，再并入 App。
5. 状态灯：先有灯效 Demo，再并入 App。

## 3. 进入 RTOS 的触发条件

满足以下条件中的两到三项，再考虑切 RTOS 更合理：

1. 主循环中出现多个独立的周期调度域，例如 5ms、10ms、20ms、100ms。
2. 音频、舵机、传感器、通信之间开始出现明显的时延干扰。
3. 某些外设交互存在阻塞，导致主状态机无法按预期前进。
4. UART、I2C、IMU、LED、BLE 等模块已经让主循环演变成手写 scheduler。
5. 需要更明确的优先级隔离和故障隔离。

## 4. 分阶段路线

### 4.1 v0.1 稳定基线

目标：把当前已实现的主板骨架固化为“稳定可联调版本”。

建议工作项：

1. 完成主板与子板单目标构建验证，固定烧录与联调流程。
2. 固定主板启动日志、模型版本日志和子板状态日志口径。
3. 验证长时间运行稳定性，包括叠框显示、KWS 心跳和子板结果读写。
4. 验证子板异常场景：未上线、启动失败、运行态掉线。
5. 校正文档中“已实现”和“设计目标”的边界。

完成标准：

1. 主板和子板各自能独立构建、烧录、联调。
2. 主板能稳定完成“先子板、后 KWS”的启动顺序。
3. 显示链路和 KWS 链路能同时持续运行。

### 4.2 v0.2 动作层与控制层

目标：引入业务动作抽象，而不是直接把 KWS 或手势结果硬连到各外设。

建议工作项：

1. 新增统一动作分发层，把 KWS、手势、未来 BLE/UWB 输入统一映射到动作。
2. 定义动作类型，例如拍照、录像开始/停止、跟随开始/结束、补光灯控制。
3. 增加主状态机，把“待机/跟随/搜索/拍照/录像”作为正式应用状态。
4. 让现有 KWS 输出不直接执行业务，而是通过动作分发层进入状态机。

完成标准：

1. KWS 识别结果不再直接散落在各模块中处理。
2. 主板业务状态机从“协议驱动”升级为“动作驱动”。

### 4.3 v0.3 云台闭环与传感器接入

目标：接入真正的控制闭环，而不是只做检测显示。

建议工作项：

1. 先接入云台控制抽象层，完成 pan/tilt 输出接口。
2. 基于 Card1 主目标框，构建最小跟随控制回路。
3. 再接入 IMU 读数和姿态输出，暂不急于做复杂融合。
4. 加入 UWB 输入解析，但先作为辅助观测源，不直接主导控制。

完成标准：

1. 主板能根据子板主目标结果驱动云台转动。
2. IMU 和 UWB 至少有日志级验证与接口层稳定输出。

### 4.4 v0.4 外围设备与用户交互

目标：补齐 BLE HID、状态灯、蜂鸣器等辅助模块。

建议工作项：

1. 接入 XM04 蓝牙 HID 控制，完成拍照和录像控制动作。
2. 接入状态灯，但优先采用单线程 `tick` 方案，不先引入独立任务。
3. 如有需要，再增加蜂鸣器或 UI 状态提示。

完成标准：

1. 至少一条用户动作链闭环可用，例如“语音拍照 -> BLE HID 输出”。
2. 辅助输出与主链路不相互干扰。

## 5. RTOS 化建议

只有在 v0.3 之后，如果主循环复杂度明显上升，再进入 RTOS 化。

如果进入 RTOS，建议按功能域划分任务，而不是按文件随意拆分：

1. 音频与 KWS 任务。
2. 子板通信与结果融合任务。
3. 云台控制任务。
4. 传感器任务，IMU 和 UWB 可先合并。
5. BLE 与外部控制任务。
6. 状态输出任务，包含 LED、蜂鸣器和调试统计。

不建议一开始就引入大量细碎任务，否则会把当前清晰的状态机优势丢掉。

## 6. 近期优先级

按实际收益排序，下一步建议优先做：

1. 完成 v0.1 的长稳验证和异常场景验证。
2. 建立统一动作分发层。
3. 接入最小云台控制闭环。
4. 再逐步加入 IMU、BLE、UWB。
5. 最后再重新评估 RTOS 是否有必要。
