# App_GimbalMaster v0.1 Validation Checklist

本文档用于把当前主板/子板 App 的 v0.1 基线验证固化成可重复执行的检查表。目标不是继续加功能，而是确认当前实现已经满足“可单独构建、可联调、主链路稳定”的最低要求。

## 1. 适用范围

当前检查表覆盖两个目标：

1. `gimbal_master` 上的 `App_GimbalMaster`
2. `gimbal_node` 上的 `App_Card1_HumanDetection`

## 2. 通过标准

只有同时满足以下条件，v0.1 才算完成：

1. 主板和子板都能单独构建。
2. 主板和子板都能单独烧录。
3. 主板与子板联调时，启动顺序、KWS、结果上报、叠框、状态灯行为一致。
4. 无子板、子板失败、运行中掉线等异常场景下，主板行为仍然可解释且日志口径一致。

## 3. 主板单目标验证

### 3.1 构建

1. 切换到 `gimbal_master` 配置。
2. 构建 `s300_gimbal_master`。
3. 如需整镜像，额外构建 `img_s300_gimbal_master`。

检查项：

1. 构建成功，无新增编译错误。
2. 当前 model manifest 与日志中的模型版本信息一致。

### 3.2 正常联机启动

前置条件：

1. 子板程序已烧录并可启动。

检查项：

1. 主板打印启动 banner、模型版本、协调服务 ready。
2. 主板先等待子板 `RUNNING`，随后才启动本地 KWS。
3. 子板 `REQUEST_MASTER_MM_ENABLE -> PREPARE_VIDEO -> START_DSP` 链路完整。
4. KWS 最终进入 `RUNNING`。
5. 状态灯从等待态切换到正常运行态。

### 3.3 画框链路

检查项：

1. 子板有有效结果时，主板显示叠框。
2. 目标消失后，主板按 debounce 清框。
3. 检测框位置、清除时机与日志一致。

### 3.4 KWS 链路

检查项：

1. 关键词日志输出正常。
2. `开始录像/停止录像/启动跟随/结束跟随/打开补光灯/关闭补光灯` 都能触发预期状态变化。
3. 状态灯短确认动画与持续状态一致。
4. 6/7 号词能实际控制 OV5640 补光灯开关。

### 3.5 无子板降级启动

前置条件：

1. 不烧录子板程序，只启动主板。

检查项：

1. 主板等待子板超时后打印 warning。
2. 主板进入 degraded mode 并启动本地 KWS。
3. 状态灯能区分 degraded mode 与正常运行态。
4. 降级模式下 KWS、状态灯、补光灯控制仍可工作。

### 3.6 异常场景

检查项：

1. 子板启动失败时，主板不会误判为正常运行。
2. 子板运行中掉线时，主板日志和灯态能反映异常。
3. KWS 初始化失败时，主板进入错误态而不是无提示停住。

## 4. 子板单目标验证

### 4.1 构建

1. 切换到 `gimbal_node` 配置。
2. 构建 `s300_card1_human_detection`。
3. 如需整镜像，额外构建 `img_s300_card1_human_detection`。

检查项：

1. 构建成功，无新增编译错误。
2. 当前模型路径和 manifest 正确。

### 4.2 单板启动

检查项：

1. 子板能正常上电启动。
2. I2C 从机寄存器区可访问。
3. 子板在未接主板时，能稳定停留在等待资源授权的合理状态。

### 4.3 联调启动

前置条件：

1. 主板程序已烧录。

检查项：

1. 子板能正确响应主板下发的 `PREPARE_VIDEO`。
2. 子板能正确响应主板下发的 `START_DSP`。
3. 子板最终进入 `RUNNING`。
4. `RESULT` 区域能持续输出检测结果。

### 4.4 结果语义

检查项：

1. 子板对外发布的数据结构保持 `subboard_detection_result_t`。
2. 当前适配层输出内容与 Human_Detection 语义一致。
3. 空结果、有结果、结果切换三种情况都能稳定发布。

## 5. 当前子板收口差距

截至当前版本，子板目标已经是正式 target，但还没有像主板一样完全完成 App 私有化收口。当前差距主要有：

1. `Projects/App_Card1_HumanDetection/CMakeLists.txt` 仍直接编译 `Projects/Demo/Subboard_MM_Consumer_Demo/Src/*.c` 多个源文件。
2. 子板 App 私有代码目前主要只有 `Src/subboard_detection_adapter.c`，核心入口、状态机、DSP 控制流仍沿用 Demo 实现。
3. 运行日志和部分源码语义仍保留 Demo 口径，边界上还不是完全干净的 App 私有实现。
4. 当前还缺一套固定的单目标验证记录，无法把“能跑”升级成“已验收”。

这意味着子板目前是“目标名和模型语义已经正式化”，但代码实现层面仍处于“基于 Demo 收口中”的状态。

## 6. 建议执行顺序

建议按以下顺序推进，而不是继续加新功能：

1. 先完成本清单中的主板异常场景验证。
2. 再完成子板单目标构建、烧录、联调验证。
3. 再决定是否要把子板核心控制流也逐步迁成 App 私有实现。
4. 只有在 v0.1 验证真正闭环后，再进入 v0.2 动作分发层。
